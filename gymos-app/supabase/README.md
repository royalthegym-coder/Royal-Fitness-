# Supabase objects added outside the main schema

- Owner's end-of-day summary (dashboard card, Hindi): table `daily_summaries`, function `daily_facts(g, d)` (aggregate numbers only, service role only), Edge function `daily-summary` (source in `functions/daily-summary/`, tests `node tests/summary.test.mjs`), pg_cron `daily-summary-final` at 16:30 UTC (22:00 IST). The text is built by fixed rules. If the Edge function values `AI_GATEWAY_API_KEY` and `AI_GATEWAY_MODEL` are added (and optionally `AI_GATEWAY_BASE_URL`, default `https://ai-gateway.vercel.sh/v1`, any OpenAI-compatible chat endpoint), the model may only re-word it, and its answer is discarded unless every number matches the database. Member names are never sent.
- Overpayment guard: trigger `payments_no_overpay` refuses a payment that would exceed its invoice total (the form also ignores a second Enter while a save is running).

- End-of-day summary on the owner's dashboard:
  - Table `daily_summaries` (one row per gym and day; owners read, only the Edge function writes), function `daily_facts(g, d)` (aggregate numbers only, service role), pg_cron `daily-summary-final` at 16:30 UTC (22:00 IST).
  - Edge function `daily-summary` (source in `functions/daily-summary/`). The text is built by fixed rules from the database numbers. If an AI gateway is configured it may only re-word it, and the answer is thrown away if any number differs, so the rules text is the fallback. No names or phone numbers are sent to the gateway.
  - Optional Edge function values (Supabase dashboard): `AI_GATEWAY_API_KEY` and `AI_GATEWAY_MODEL` (both needed), `AI_GATEWAY_BASE_URL` (default `https://ai-gateway.vercel.sh/v1`, any OpenAI-compatible gateway works).
- Payments can no longer exceed their invoice: trigger `payments_no_overpay` (a double Enter press had saved the same ₹2000 twice; the form also ignores a second submit while saving).

- Diet + workout plans:
  - Tables `member_fit` (body details, one row per member) and `member_plans` (kind diet/workout, status draft/published/archived). Staff of the gym read and write; a member reads only their own PUBLISHED plans; only staff can publish (RLS verified with rollback tests).
  - Edge function `generate-plan` (verify_jwt = true, runs as the caller so RLS applies; source in `functions/generate-plan/`). All numbers (BMR/TDEE, calories, macros, portions, sets, reps) come from fixed rules in `engine.js` (unit tests: `node tests/plan-engine.test.mjs`). Injuries and allergies remove unsafe exercises and foods; health conditions, allergies, under-18 members mark the draft "needs review"; pregnancy or breastfeeding is refused (refer to a doctor).
  - Optional: if the Edge function value `ANTHROPIC_API_KEY` is added in the Supabase dashboard, Claude writes only a short personal note and tips. It never changes a number. Without it everything still works.

- Automatic WhatsApp (receipt after payment, expiry reminder, due reminder):
  - Tables `wa_settings` (per-gym switches, days, template names) and `wa_log` (queue and history; unique `dedupe_key`, so a message is never queued twice); column `members.wa_opt_out`.
  - Queueing: trigger `wa_payment_receipt` on `payments`; pg_cron `wa-daily-reminders` at 03:30 UTC (09:00 IST) runs `private.wa_daily_job()`; `wa-queue-retry` pokes the sender every 5 minutes while anything is queued.
  - Sending: Edge function `wa-dispatch` (verify_jwt = false, authenticates inside) sends Meta WhatsApp Cloud API template messages. pg_cron and the trigger call it with a random shared value kept in Supabase Vault and checked through `wa_cron_ok`; the in-app buttons use the signed-in admin's session.
  - The owner must add two Edge function values in the Supabase dashboard: `WHATSAPP_TOKEN` and `WHATSAPP_PHONE_NUMBER_ID`. Until then messages stay queued (anything older than 3 days is dropped). The guide and the three template texts are on the app's WhatsApp page.

- Expenses and leads:
  - Table `expenses` (owner only, fixed categories, amount > 0) feeds the Expenses & profit page (fees collected minus expenses). Table `leads` (owner and trainers read/insert/update, only the owner deletes) feeds the Leads page: stages New, Contacted, Trial, Converted, Lost; follow-up dates; "Make member" opens the member form prefilled and marks the lead Converted only after the member is saved. Both tables are gym-scoped by RLS and stop accepting writes when the gym is locked (rollback-tested).
  - Function `admin_set_gym_timings(gym, timing_text)` and column `gyms.timings`: the owner sets opening hours in Edit gym; members see them on their page.

- Store / POS: tables `products` (owner manages, staff read) and `sales` (staff read only; nobody can write it directly, so history cannot be edited). `record_sale(product, qty, method, member)` locks the product row, refuses more than the stock, snapshots price and cost, and lowers stock in one step; `void_sale(sale)` (owner only, idempotent) marks the sale cancelled and adds the stock back. The Expenses & profit page adds store profit (sales minus cost of goods, cancelled sales left out). Rollback-tested as owner, trainer and member. Cost prices are owner-only at the database level: they live in `product_costs` and `sale_costs` (RLS: gym owner only). The old `products.cost` and `sales.unit_cost` columns are kept but locked to 0 by a check constraint. Products are saved through `save_product(...)` (owner only, writes the product and its cost together). Rollback-tested: a trainer sees 0 cost rows, can still sell, cannot save products.

  Caller role and gym come from the database, never from the request. Deployed to project `ayoeevltbubkyhixqqlg`.

- Staff & salary (owner only): tables `staff_members` (name, job, phone, monthly salary, joined date, active) and `salary_payments` (month `YYYY-MM`, kind salary/advance/bonus, amount > 0, method, date). RLS: only the gym owner can read or write, and only while the gym is open; trainers and members see nothing. Payments cannot be edited (no update grant), only deleted by the owner, and every delete is written to `audit_log` (`delete_salary_payment`) by trigger `private.salary_payment_deleted`. Rollback-tested: the owner can add staff and payments; a bad month, a negative amount and any update are refused; a trainer and a member see 0 rows and cannot insert. Also verified: deleting a payment writes one `audit_log` row, a person with payments cannot be deleted, and a person without payments can.

Members see it on the "My progress" page, staff from the member card ("Progress"). Rollback-tested: staff insert, staff-posing-as-member, member-posing-as-staff, other member, other gym, bad ranges, empty row and future date are all handled as above.

- Trainer assignment: columns `members.trainer_id` (profile of a trainer or the owner in the same gym) and `members.trainer_name` (copied by trigger `members_trainer_guard`, so a member can see their trainer's name without reading other profiles; it cannot be edited directly). ## Online fee payment (Razorpay Payment Links)

- Tables `online_pay` (per gym on/off, set only by the super admin through `set_online_pay`) and `online_orders` (one row per payment link; members see their own, owners see their gym's; nobody can write from the browser).
- Edge Function `razorpay` (verify_jwt off because Razorpay's webhook carries no JWT; app calls are authenticated with the user's token inside the function). Actions: `status`, `create` (invoice id only; the amount due is worked out by the database in `rz_begin`), and the signed webhook (`X-Razorpay-Signature`, HMAC-SHA256 of the raw body, constant-time compare).
- `rz_apply_payment` (service role only) records the payment once: unique Razorpay payment id, row lock, amount must equal the order, invoice must not be cancelled. Anything else (amount mismatch, already paid in cash, cancelled invoice) is parked as `review` for the owner instead of failing silently. The normal payment triggers then run (receipt number, secure ledger, activity log, WhatsApp receipt).
- Edge Function values you enter yourself in the Supabase dashboard: `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET`. Razorpay webhook URL: `https://<project>.supabase.co/functions/v1/razorpay`, events `payment_link.paid`, `payment_link.expired`, `payment_link.cancelled`.
- Money settles to the one Razorpay account whose keys are saved, so switch a gym on (Super admin, Gyms, Online pay) only if it belongs to that account. Per-gym Razorpay accounts are a later step.
- Links expire after 2 hours; a link for the same invoice and amount is reused for 30 minutes. Razorpay sends no SMS or email itself. Rollback-tested in the database (off by default, stranger refused, repeated webhook recorded once, mismatch and overpay parked). The live Razorpay round trip cannot be tested from the build sandbox, so test once in Razorpay Test mode.

## Push notifications (Web Push)

- Tables `push_subs` (one row per phone or browser; a person reads only their own), `push_outbox` (queue and log; owners read their gym's), `push_config` (the server's own VAPID key pair, readable only by the service role). No key has to be typed anywhere: the `push-dispatch` Edge Function makes the pair on first use and the private half stays in the database.
- Members switch notifications on in Profile (`push_subscribe` / `push_unsubscribe`, at most 5 devices each). Nothing is queued for a person who has no device registered.
- What is sent: payment recorded (trigger `push_on_payment`), membership ends today or in 2 days (pg_cron `push-daily-expiry` at 03:45 UTC = 09:15 IST, one message per member and end date), and owner announcements (`push_announce`, owner only, 1 to 60 character title, up to 200 character message, one announcement per 10 minutes per gym; `push_stats` gives the counts).
- Delivery: `private.push_kick()` calls `push-dispatch` (verify_jwt off; the flush call is authorised with the same vault secret as `wa-dispatch`) and `push-queue-retry` pokes it every 5 minutes. A device the phone has removed (HTTP 404 or 410) is deleted; a temporary failure retries up to 3 times; a message older than that is marked failed.
- Tapping a notification opens the app only on a page of the same site (`sw.src.js`, `safePath` in the function). On iPhone web push works only after "Add to Home Screen".
- Rollback-tested in the database (no device means no row, stranger and member refused on every owner or server function, receipt text, expiry message not repeated, announcement rate limit). The real delivery to a phone cannot be tried from the build sandbox: after deployment switch notifications on from a phone and press "Send me a test".

## AI coach

- Tables `coach_settings` (per gym `enabled`, default off, and `daily_limit` 1 to 50; readable by the owner and the super admin) and `coach_messages` (a member reads only their own chat; the app cannot write to it, the Edge Function writes with the service role). Migration: `supabase/migrations/20261116_ai_coach.sql`.
- `coach_begin(text)` runs as the signed-in member and does every check in the database: member with a linked membership, gym open, gym switch on, question 2 to 500 characters, daily limit per member, 500 questions per gym per day, 4 seconds between questions. It stores the question and returns what the model may use: first name, age, height, weight, goal, diet preference, injuries/conditions/allergies from the member's own profile, the summary of the published diet and workout plans, and visits in the last 30 days. Never phone number, date of birth, payments or other members.
- `set_coach(gym, enabled, limit)`: the super admin can set anything (Super admin, Gyms, AI coach). A gym owner may only switch it OFF for their own gym. `coach_stats` gives the owner counts only; the owner cannot read a member's questions. `coach_clear` lets a member delete their own chat. Only the newest 60 messages per member are kept.
- Edge Function `ai-coach` (verify_jwt on). Actions `status` and `ask`. It uses the same secrets as the daily summary: `AI_GATEWAY_API_KEY`, `AI_GATEWAY_MODEL` and optionally `AI_GATEWAY_BASE_URL` (default `https://ai-gateway.vercel.sh/v1`, OpenAI-compatible chat completions). Values are entered by the owner in the Supabase dashboard (Edge Functions, Secrets), never in chat. Without them members see "being set up" and nothing is invented.
- Safety: before any model call, `screen()` in `lib.js` catches self-harm, medical red flags and conditions, pregnancy, eating disorders, drugs/hormones/weight-loss medicines and pain/injury (English, Hindi, Hinglish). Those get a fixed answer (doctor, trainer, helplines 14416 and 112) and the model is not called. The prompt is built on the server; the member's text and profile are data inside tags and the model is told to ignore instructions inside them. The model's answer is checked and replaced by a fixed "ask your trainer" text if it contains a medicine dose, a diagnosis, or a prompt leak. If the gateway fails, the question is removed so it does not count against the member.
- Privacy: the facts listed above, including injuries, conditions and allergies, are sent to the AI gateway provider with each question. Members should be told this in the app before the switch is turned on for their gym.
- Tests: `tests/coach.test.mjs` (screening, prompt, facts, answer checks), `tests/coachui.test.mjs` (page helpers), e2e block "AI coach". The gateway itself cannot be exercised from the build sandbox: after saving the secrets, switch the coach on for one gym and ask one real question as a member.

## EMI plans (installments)

An owner can split a fee a member already owes into 2 to 12 installments with fixed due dates. The money stays where it always was: the invoice and its payments. A plan only says how much should be covered by which date. Any payment (cash, UPI or online) counts toward the earliest installment that is not covered yet.

Files:
- `migrations/20261116_emi_plans.sql`: tables `emi_plans` and `emi_installments` (RLS: the gym's owner, or the member who owns the invoice); `private.emi_calc` (the one place states are worked out); `emi_schedule`, `emi_create_plan`, `emi_cancel_plan`, `rz_begin_part`; `private.emi_daily_job` and the cron job `push-emi-daily` (03:50 UTC, 09:20 IST).
- `migrations/20261117_emi_skip_cancelled.sql`: reminders skip cancelled invoices.
- `functions/razorpay/index.ts`: `create` accepts `part: true` and then calls `rz_begin_part`, so only the next installment is charged. The Razorpay page says "EMI" for those links.
- `src/c37-emi.js`: owner page and form, member card. The pure functions (split, due dates, limits, next amount) are tested in `tests/emi.test.mjs`.

Rules:
- Split: equal parts in paise; the last installment takes the rounding difference.
- Due date: start + n months. A day the month does not have becomes its last day (31 Jan + 1 month = 28 Feb).
- Start date: from today up to 62 days ahead. 2 to 12 installments.
- One active plan per invoice (unique index). Cancelling a plan leaves the invoice and its payments unchanged.
- States: `paid` (payments cover the installment's cumulative amount), `overdue` (past its date, not paid), `due_today`, `upcoming`.
- Online: the member pays only the next unpaid installment (the rest of it if part was paid). The full-balance button stays. The webhook records the payment exactly as before, because `rz_apply_payment` checks the order amount.
- Reminders: 2 days before, on the due day, and the day after, once each per installment (dedupe key `emi:<plan>:<seq>:<offset>`). Only for members with a push subscription, only for open gyms, never for cancelled invoices.

Testing:
- Unit: `node tests/emi.test.mjs`.
- Database: rollback test on the live project (raise REPORT, then roll back). It covered: the split, duplicate refused, count and start limits, cash and online states, the online amount for the next installment, order reuse, another member refused, cancel and re-create, a member sees only own rows, direct insert refused, overdue state, reminders with dedupe and without a push subscription, and cancelled invoices skipped.
- E2E: the "EMI plans" block in `tests/e2e.cjs`.

Not verifiable in the sandbox: a real Razorpay payment of an installment, push delivery to phones, and the cron run at 03:50 UTC.

Deploy: migrations are applied in order. Redeploy the `razorpay` function after this change (verify_jwt false, as before).
