# Supabase objects added outside the main schema

- Owner's end-of-day summary (dashboard card, Hindi): table `daily_summaries`, function `daily_facts(g, d)` (aggregate numbers only, service role only), Edge function `daily-summary` (source in `functions/daily-summary/`, tests `node tests/summary.test.mjs`), pg_cron `daily-summary-final` at 16:30 UTC (22:00 IST). The text is built by fixed rules. If the Edge function values `AI_GATEWAY_API_KEY` and `AI_GATEWAY_MODEL` are added (and optionally `AI_GATEWAY_BASE_URL`, default `https://ai-gateway.vercel.sh/v1`, any OpenAI-compatible chat endpoint), the model may only re-word it, and its answer is discarded unless every number matches the database. Member names are never sent.
- Overpayment guard: trigger `payments_no_overpay` refuses a payment that would exceed its invoice total (the form also ignores a second Enter while a save is running).

- End-of-day summary on the owner's dashboard:
  - Table `daily_summaries` (one row per gym and day; owners read, only the Edge function writes), function `daily_facts(g, d)` (aggregate numbers only, service role), pg_cron `daily-summary-final` at 16:30 UTC (22:00 IST).
  - Edge function `daily-summary` (source in `functions/daily-summary/`). The text is built by fixed rules from the database numbers. If an AI gateway is configured it may only re-word it, and the answer is thrown away if any number differs, so the rules text is the fallback. No names or phone numbers are sent to the gateway.
  - Optional Edge function values (Supabase dashboard): `AI_GATEWAY_API_KEY` and `AI_GATEWAY_MODEL` (both needed), `AI_GATEWAY_BASE_URL` (default `https://ai-gateway.vercel.sh/v1`, any OpenAI-compatible gateway works).
- Payments can no longer exceed their invoice: trigger `payments_no_overpay` (a double Enter press had saved the same ₹2000 twice; the form also ignores a second submit while saving).

- Diet + workout plans:
  - Tables `member_fit` (body details, one row per member) and `member_plans` (kind diet/workout, status draft/published/archived). Staff of the gym read and write; a member reads only their own PUBLISHED plans; only staff can publish (RLS verified with rollback tests).
  - Edge function `generate-plan` (verify_jwt = true, runs as the caller so RLS applies; source in `functions/generate-plan/`). All numbers (BMR/TDEE, calories, macros, portions, sets, reps) come from fixed rules in `engine.js` (unit tests: `node tests/plan-engine.test.mjs`). Injuries and allergies remove unsafe exercises and foods; health conditions, allergies, under-18 members mark the draft "needs review"; pregnancy or breastfeeding is refused (refer to a doctor).
  - Optional: if the Edge function value `ANTHROPIC_API_KEY` is added in the Supabase dashboard, Claude writes only a short personal note and tips. It never changes a number. Without it everything still works.

- Automatic WhatsApp (receipt after payment, expiry reminder, due reminder):
  - Tables `wa_settings` (per-gym switches, days, template names) and `wa_log` (queue and history; unique `dedupe_key`, so a message is never queued twice); column `members.wa_opt_out`.
  - Queueing: trigger `wa_payment_receipt` on `payments`; pg_cron `wa-daily-reminders` at 03:30 UTC (09:00 IST) runs `private.wa_daily_job()`; `wa-queue-retry` pokes the sender every 5 minutes while anything is queued.
  - Sending: Edge function `wa-dispatch` (verify_jwt = false, authenticates inside) sends Meta WhatsApp Cloud API template messages. pg_cron and the trigger call it with a random shared value kept in Supabase Vault and checked through `wa_cron_ok`; the in-app buttons use the signed-in admin's session.
  - The owner must add two Edge function values in the Supabase dashboard: `WHATSAPP_TOKEN` and `WHATSAPP_PHONE_NUMBER_ID`. Until then messages stay queued (anything older than 3 days is dropped). The guide and the three template texts are on the app's WhatsApp page.

- Expenses and leads:
  - Table `expenses` (owner only, fixed categories, amount > 0) feeds the Expenses & profit page (fees collected minus expenses). Table `leads` (owner and trainers read/insert/update, only the owner deletes) feeds the Leads page: stages New, Contacted, Trial, Converted, Lost; follow-up dates; "Make member" opens the member form prefilled and marks the lead Converted only after the member is saved. Both tables are gym-scoped by RLS and stop accepting writes when the gym is locked (rollback-tested).
  - Function `admin_set_gym_timings(gym, timing_text)` and column `gyms.timings`: the owner sets opening hours in Edit gym; members see them on their page.

- Store / POS: tables `products` (owner manages, staff read) and `sales` (staff read only; nobody can write it directly, so history cannot be edited). `record_sale(product, qty, method, member)` locks the product row, refuses more than the stock, snapshots price and cost, and lowers stock in one step; `void_sale(sale)` (owner only, idempotent) marks the sale cancelled and adds the stock back. The Expenses & profit page adds store profit (sales minus cost of goods, cancelled sales left out). Rollback-tested as owner, trainer and member. Cost prices are owner-only at the database level: they live in `product_costs` and `sale_costs` (RLS: gym owner only). The old `products.cost` and `sales.unit_cost` columns are kept but locked to 0 by a check constraint. Products are saved through `save_product(...)` (owner only, writes the product and its cost together). Rollback-tested: a trainer sees 0 cost rows, can still sell, cannot save products.

- Edge function `create-account` (verify_jwt = true): a gym admin creates a trainer/member login for their OWN gym.
  Caller role and gym come from the database, never from the request. Deployed to project `ayoeevltbubkyhixqqlg`.
- SQL function `public.service_assign_profile(...)`: executable only by `service_role`; sets role/gym on the new profile and links the member.
- SQL function `public.admin_update_gym(...)`: super admin or that gym's admin; edits name/owner/phone/city/UPI only.
- Table `public.offers` (RLS: staff + gym members read, gym admin writes while the gym is open); columns `members.photo_path`, `members.reminded_on`.
- Private Storage bucket `member-photos` (max 512 KB, jpeg/png/webp); object path `<gym_id>/<member_id>.jpg`; policies limit access to that gym's staff and the member themself.

- Staff & salary (owner only): tables `staff_members` (name, job, phone, monthly salary, joined date, active) and `salary_payments` (month `YYYY-MM`, kind salary/advance/bonus, amount > 0, method, date). RLS: only the gym owner can read or write, and only while the gym is open; trainers and members see nothing. Payments cannot be edited (no update grant), only deleted by the owner, and every delete is written to `audit_log` (`delete_salary_payment`) by trigger `private.salary_payment_deleted`. A person with payment history cannot be deleted (foreign key restrict); mark them as left instead. The Expenses & profit page counts salaries paid in the selected month as expenses. Rollback-tested: the owner can add staff and payments; a bad month, a negative amount and any update are refused; a trainer and a member see 0 rows and cannot insert. Also verified: deleting a payment writes one `audit_log` row, a person with payments cannot be deleted, and a person without payments can.

- Member progress: table `member_progress` (weight, body fat, waist, chest, hips, arm, thigh, note; at least one value; sane ranges; no future dates). RLS: staff of the gym read, add, edit and delete; a member reads only their own rows and can add their own (the row is marked `by_member = true`; staff rows must be `false`, so one cannot pose as the other); members cannot edit or delete. Members see it on the "My progress" page, staff from the member card ("Progress"). Rollback-tested: staff insert, staff-posing-as-member, member-posing-as-staff, other member, other gym, bad ranges, empty row and future date are all handled as above.

- Trainer assignment: columns `members.trainer_id` (profile of a trainer or the owner in the same gym) and `members.trainer_name` (copied by trigger `members_trainer_guard`, so a member can see their trainer's name without reading other profiles; it cannot be edited directly). Only the gym owner can assign or change a trainer; a trainer from another gym is refused; trainers can still edit other member fields. Rollback-tested. The Members page has "Everyone / My members / No trainer" filters, the owner picks the trainer in the member form, the member sees "My trainer" on their profile, and the members CSV has a Trainer column.

- Trainer commission (owner only): table `trainer_commission` (one rate per trainer, 0 to 100 percent, trainer must belong to the gym). Trainers and members see nothing. The Staff & salary page shows, per month, each trainer's members, fees collected from them and the commission at the set rate. It is a report; the owner records the payout as a Bonus in staff payroll. Rollback-tested (duplicate, over 100, other-gym trainer, trainer and member access).

- Classes and bookings: tables `gym_classes` (title, coach, start time, minutes, capacity, note, cancelled) and `class_bookings`. Staff create, edit and cancel classes (only the owner can delete); everyone in the gym reads them. Nobody writes bookings directly: `book_class(class, member)` locks the class row and refuses a full class, a double booking, a cancelled or already started class, an expired membership and a locked gym; a member can only book for themself, staff can book any member. `cancel_booking(booking)` lets a member cancel their own spot until 2 hours before the start (staff any time). `class_booked_counts(gym)` returns the number booked per class without exposing other members. Rollback-tested as owner and as member. The app has a Classes page (staff, with weekly repeat) and a "Book a class" page for members.

- QR check-in (no database change): the member's home page shows a QR pass (`gymos:<member id>`, drawn in the browser, works offline). Staff scan it on the Check-in page with the phone camera (needs a browser with a built-in QR reader, e.g. Chrome) or with a USB/Bluetooth barcode scanner into the code box. A scan checks the member in, or out if they are already inside today; expired, frozen and cancelled members and codes from another gym are refused. The check-in itself is still the normal `visits` insert that only staff can do, so a copied QR cannot check anyone in without a staff member present. The QR generator was verified by decoding it with an independent QR reader.

- Staff tasks: table `gym_tasks` (title, note, priority Low/Medium/High, due date, assignee, done time). Staff of the gym (owner and trainers) read, add, edit and mark done; only the owner deletes; the assignee must be an owner or trainer of the same gym; members see nothing. Rollback-tested as owner, trainer and member.

- Birthdays: column `members.dob` (date, optional, between 1900-01-01 and 2100-01-01; the app also refuses future dates). The Reminders page lists members whose birthday falls in the next 7 days (cancelled members skipped; 29 Feb is celebrated on 28 Feb in common years) with a ready WhatsApp greeting. Members keep the same row-level rules as before: staff of the gym edit it, a member reads only their own row. Tested: `tests/birthday.test.mjs` (date maths) and the browser test (future date refused, birthday card with WhatsApp link).

- Achievements (no database change): the member home shows a level (Starter, Regular, Strong, Elite) and 8 badges (1, 10, 25, 50 training days; 3, 7, 14, 30 days in a row), worked out in the browser from the member's own `visits` rows, which row-level security already limits to that member. Counted over the last 90 days only (the window the app loads), and it is shown on the card. Nothing is stored, so nothing can be edited or faked. Tested: `tests/achievements.test.mjs` plus the browser test.

- Google review link: column `gyms.review_url` (https and a Google address only: search.google.com, www.google.com, google.com, g.page, maps.app.goo.gl, goo.gl; no spaces; up to 300 characters; enforced by a check constraint) and owner-only function `admin_set_gym_review_url(gym, link)` (security definer, owner of that gym or platform admin, audit logged). Members read it through the existing `gyms_read` policy and see a Write a review button; the owner sees a QR on the Settings page (drawn in the browser; links over 106 bytes get a note to use the short g.page link). Tested in a rolled-back transaction: good link saved; http, a look-alike host and a link with a space refused; direct table update refused; a trainer refused. Browser test covers the form, the QR and the member button.

- Referrals: column `members.referred_by` (member of the same gym; `on delete set null`) and trigger `members_referrer_guard` (cannot refer yourself, referrer must exist in the same gym). Only staff edit it in the member form; a member still reads only their own row. The Reminders page shows top referrers with a WhatsApp thank-you. The app counts referrals only and promises no reward. Tested in a rolled-back transaction (valid, self and unknown referrer, referrer deleted) and in the browser test.

- Membership freeze: table `member_freezes` (started, ended, days added, reason; one open freeze per member) is written only by two owner-only functions, `freeze_member(member, why)` and `unfreeze_member(member)` (security definer, gym must be open, audit logged). Freezing needs a running, not cancelled, not already frozen membership; unfreezing moves `members.end_date` by the days frozen (Indian date) and returns that number. Staff and the member themself can read the history; direct insert, update or delete is revoked. A frozen member cannot be checked in. Tested in a rolled-back transaction (freeze, double freeze, expired, direct insert, unfreeze with a 5-day shift, second unfreeze, trainer refused) and in the browser test.

- Equipment register: table `gym_equipment` (name, condition Working/Needs repair/Out of order, service every N days 1-730, last service date not in the future, vendor, note). Staff of the gym read, add and edit; only the owner deletes; the gym cannot be changed by an update. The page shows next service dates and what is overdue. Browser test passes. NOT YET tested against the live database with a rolled-back transaction (the test prompt timed out); the row-level rules copy the tested `gym_tasks` ones.

- Last 7 days card (no database change): the owner dashboard compares the last 7 days with the 7 before (collected, new members, check-ins, members who came) from `payments`, `members` and `visits`, which the owner already reads, plus memberships ending in 7 days and pending dues, with a WhatsApp share button. Tested: `tests/weekly.test.mjs` (date windows, frozen and future rows, divide by zero) and the browser test.

- Workout log: table `member_workouts` (exercise, sets 1 to 30, reps 1 to 200, weight 0 to 1000 kg, note, date not more than a day ahead). RLS: staff of the gym and the member themself read; only the member adds and deletes their own entries (the gym must be open); nobody can update (delete and add again); no access for anonymous users. Personal records (heaviest set, then most reps; body-weight exercises by reps), the Epley estimate for 1 to 10 reps and weekly volume are worked out in the browser, never stored. Trainers and the owner see it read-only from the member window. Tested in a rolled-back transaction (own insert and delete, another member and staff insert refused, bad values refused, update refused, other members see nothing), `tests/workouts.test.mjs` and the browser test.

- Daily habits: tables `member_water` (50 to 2000 ml per entry), `member_meals` (Breakfast, Lunch, Snack or Dinner; food, calories 0 to 5000, protein, carbs, fat) and `member_sleep` (hours 0.5 to 16, quality 1 to 5, one night per day per member). Dates cannot be more than a day ahead. RLS is the same for all three: staff of the gym and the member read; only the member adds and deletes their own rows (the gym must be open); no update, no anonymous access. Staff see it read-only in the member window so a trainer can coach; remove the staff clause in the read policies if you prefer these private to the member. Totals, averages and the 3 litre water guide are worked out in the browser. The built-in food list holds typical approximate values and says so. Tested in a rolled-back transaction (own insert and delete, others refused, ranges, duplicate night, update, anonymous), `tests/wellness.test.mjs` and the browser test.

- Gym leaderboard (opt-in): column `members.leaderboard_opt_in` (default false), trigger `members_leaderboard_guard` (nobody except the member, through `set_my_leaderboard`, can change it; staff edits are refused and new rows always start false), `gym_leaderboard()` (security definer; top 10 of opted-in, non-cancelled members of the caller's own gym by distinct training days this month in IST, plus the caller's own row; shows first name and last initial only) and `set_my_leaderboard(opt)`. Members see the list only after joining. Tested in a rolled-back transaction: staff toggle refused, new rows false, non-joined members hidden, two visits on one day count once, last month and cancelled members excluded, opt-out removes the member, anonymous refused; plus the browser test.
